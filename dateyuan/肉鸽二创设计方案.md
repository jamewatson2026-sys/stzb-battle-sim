## 一、作品定位与目标

### 1.1 这是什么

> **一款「抽卡养成 + 关卡推进」的纯卡牌肉鸽**：以《率土之滨》式三将三战法战斗为结算内核，
> 玩家靠**五连抽 + 五选一**组建卡池、靠**重复武将的红度复利**滚强、靠**通关奖励**补战法与宝物，
> 一路打过关卡。战斗全自动，决策全在战前与卡池经营。

### 1.2 求职作品意味着什么（会改变取舍）

| 评价维度 | 对本设计的约束 |
|---|---|
| **可演示** | 打开就能玩、3 分钟内能看懂在干什么；不能出现"要跑脚本才有东西看" |
| **架构可讲** | 引擎 / 玩法层 / 表现层三层解耦，玩法层零 DOM、可单测、可整体搬进 Unity（见 §九） |
| **可测试** | 覆盖关键不变量的单测；用 `tests/__snapshots__/golden.json` 证明引擎零改动 |
| **数据驱动** | 抽卡定价、品级、红度阶梯、关卡曲线全部是**参数表**而非硬编码（见 §四、§五） |
| **平衡可量化** | 用蒙特卡洛胜率（现成 `web/winRate.ts`）说明"越抽越强"是可测量的，不靠主观感受 |

> 因此：**长线留存、元进度、赛季续命这些"运营向"设计一律不做**（§十四），把预算全押在"演示效果 + 工程质量"上。

### 1.3 肉鸽要素自检

肉鸽必要条件分三层：**定义层**（Berlin Interpretation 八要素）、**结构层**（局内闭环 / 程序化决策 / 重代价失败 / 构筑协同 / 元进程 / 资源经济）、**体验层**（随机可读、失败可归因、难度曲线、单局时长）。其中"回合制 / 格子制"是低价值要素——这也是本方案敢做"无地图"的依据。

| # | 必备要素 | v1.0 如何满足 | 落在哪节 |
|---|----------|----------------|----------|
| 1 | 局内闭环（20–60 分钟） | 12 关 / 3 幕；开局抽卡 → 组队 → 出战 → 战报 → 奖励/商店 | §三 |
| 2 | 程序化**决策**序列 | **五选一**（把抽卡随机转成选择）+ 商店取舍 + 每关组队 | §四、§三 |
| 3 | 永久死亡 / 重代价失败 | 命数 3，被斩首 -1；兵力跨关累计、死兵永久 | §六、§八 |
| 4 | 构筑与协同 | 卡池（武将）+ 战法背包（初始 B 级 + 购买 A/S）+ 宝物；红度复利 | §四、§五 |
| 5 | 元进程 | **v1 自觉不做**（求职作品不需要），见 §十四 | §十四 |
| 6 | 资源经济与风险回报 | **玉符单币种**：抽将 or 买指定战法，二者互斥取舍 | §四 |
| 7 | 随机**可读可规划** | 敌方情报全公开 + 引擎确定性 seed + 蒙特卡洛胜率 | §三、§十 |
| 8 | 失败**可归因** | `diagnosis.ts` 的败因归因（克制 / 控制 / 主战法空转 / 出手顺序）进战报页 | §十一 |
| 9 | 难度曲线 | 目标胜率 0.90 → 0.40；"越抽越强"应表现为胜率与斩首速度同时上移 | §十、§十三 |
| 10 | 单局时长控制 | 战斗是毫秒级模拟、战报可快进 → 节奏由决策决定，不是看动画 | §三、§十一 |

**唯一自觉缺口是 #5 元进程**——它与"抽卡复利"功能重叠，且对求职作品无增益。

## 三、核心循环（v1.0）

```
【开局】
  3000 玉符
    └─ 五连抽 ×3（每次 950）
         每次：抽 5 张 → 五选一入池 → 点「爽玩」免费随机 +1
         三次后：卡池 ≈ 6 将，玉符剩 ≈150

【每关】
  ① 敌方情报全公开（武将/战法/兵力/兵种/站位）
  ② 组队：从卡池挑 3 将 → 配战法（B 级自有 + 已购 A/S）→ 宝物 / 兵种 / 站位
  ③ 出战：runBattle 自动结算（确定性 seed，毫秒级）
  ④ 战报：逐回合时间轴 + 统计 + （二期）越界高亮
  ⑤ 结算：
       胜 → 玉符 + 随机 S/A 战法 或 宝物 → 进下一关
       败 → 扣 1 条命，可换阵容重打本关
       平 → 不扣命、无奖励、可重打
  ⑥ 商店（随时可进）：花玉符买**指定** A/S 战法

【终局】
  12 关全通 → cleared ｜ 命数归零 → dead → 结算展示
```

**胜负判定**（详见 §六）：引擎是**斩首制**；打满 8 回合双方大营都活时由 `judgeOutcome()` 按剩余兵力比判高者胜。

## 四、经济系统（玉符单币种）

### 4.1 设计意图

玉符是**唯一货币**，它只有两个出口，而且**互相排斥**：

```
玉符 ──┬─→ 五连抽（950）      : 换「武将」，方向是拓宽卡池 / 攒红度
       └─→ 商店买战法（A/S）   : 换「战法」，方向是立刻变强
```

这个二选一就是 v1 的**核心取舍**：抽卡是"赌未来+复利"，买战法是"买当下强度"。**不要**给它加第三种货币——单币种是这套经济的可讲之处。

### 4.2 参数表（全部可调，集中在 `src/rogue/economy.ts`）

| 参数 | v1 取值 | 说明 |
|---|---|---|
| 开局玉符 | **3000** | 用户指定 |
| 五连抽单价 | **950** | 见 §4.3 口径说明 |
| 每次五连抽产出 | **2 张武将**（五选一 1 张 + 爽玩随机 1 张） | |
| A 级战法售价 | **600** | 待调参 |
| S 级战法售价 | **1200** | 用户要求"S 稍高，避免没有难度" |
| 单关通关玉符 | **500** | 待调参 |
| 通关附赠 | 随机 1 件：**S/A 战法 或 宝物** | 用户指定 |
| 一局总可支配（12 关） | ≈ 3000 + 500×12 = **9000** | 若全买 S 级 ≈ 7 件；若全抽卡 ≈ 9 次五连抽（18 将） |

> **平衡锚点**：S 级单价 1200 ≈ 2.4 关的收益。让玩家"买得起但买不满"，逼出取舍——这就是用户说的"避免没有难度"的落地方式。

### 4.3 抽卡口径（⚠️ 一处需要确认的读法）

用户原话："开局有获得 3000 玉符，每 950 可从大武将池中进行三次五连抽。"

**本文采用的口径**：**五连抽单价 950 玉符；开局 3000 恰好支持 3 次五连抽**（3000 = 950×3 + 150 余）。

> 若你的本意是"950 玉符买 3 次五连抽"（即 950 → 15 张卡），则开局会得到 9 次五连抽 / 18 张将，卡池过宽、红度复利会被稀释。**实现方按本文口径做；若用户改口，只改 `economy.ts` 一个常量与 §4.2 表格。**

### 4.4 抽卡交互（三步，缺一不可）

| 步 | 交互 | 设计作用 |
|---|------|----------|
| 1 | **五连抽**：从大武将池随机抽 5 张展示 | 随机性 + 多巴胺 |
| 2 | **五选一**：玩家从这 5 张里挑 **1 张**入池 | **把随机转成决策**——这是本作"有得选"的关键，也是肉鸽要素 #2 的落点 |
| 3 | **「爽玩」**：点击后**免费**再从武将池随机抽 1 张入池 | 固定的小奖，保证每次抽卡都有"净赚"的正反馈 |

**抽卡池**：`web/heroes.ts` 里的**已上架武将**（`mainSkillId` 已实现者，实测 **159 个** / 总数 162）。**必须复用配将台同一套过滤**（`isHeroListed`），否则会抽到无法上阵的武将。

**重复判定按 `heroId` 精确匹配**——SP 赵云与赵云是两张不同的卡（`mutualExclusionGroup` 决定它们不能同队，但不影响"是否算重复"）。

### 4.5 商店（指定购买）

- 出售 **A 级（127 个）/ S 级（93 个）** 全部战法，玩家**指定**购买
- **不卖 B/C/D 级**——因为 B 级及以下初始就有（见 §4.6）
- 已拥有的战法不再上架；同一战法不可重复购买

### 4.6 初始战法：为什么建议"B 级及以下全给"

既有数据里的品级是**五档**：**D 34 / C 47 / B 85 / A 127 / S 93 = 386 个**（`web/data/skill_grades.json`）。

用户口径是"初始拥有所有 B 级战法"。本文扩展为 **初始拥有 D + C + B 全部（共 166 个）**，理由是：
1. C/D 级严格弱于 B 级，若做成"可以买"会立刻暴露"没人会买"的定价荒谬；
2. 商店只卖 A/S，货架语义干净：**"基础免费，进阶付费"**。

> ⚠️ **由此产生的真实风险（必须处理）**：一开局就有 166 个可用战法、每将只有 2 个可学槽位、一队要配 6 个战法 → **选择过载**。对策（§十七有完整清单）：按兵种/类型/品级筛选 + 排序 + "可装备"标记（复用现成 `web/teamConfig.ts` 战法面板的筛选能力），**不要**做成一列 166 项的裸下拉。

## 五、武将与红度成长（重复获得的复利）

### 5.1 红度阶梯（用户口径）

| 第几次获得该武将 | 红度 | 等级 | 相对首次获得的增量 |
|---|---|---|---|
| 第 1 次 | 0 红 | 40 | — |
| 第 2 次 | **2 红** | 40 | +20 自由属性点 |
| 第 3 次 | **4 红** | 40 | +40 自由属性点 |
| 第 4 次及以后 | **满红 5 红** | **50** | +60 自由属性点、**+2000 兵力** |

> 第 4 次之后重复获得：**不再变化**（已是满配）。可选：折算为少量玉符（v1 建议**先不做**，避免复杂度）。

### 5.2 与既有战斗系统的口径对齐（实测，非新造）

两条公式都**已存在于引擎侧**，肉鸽层只负责按上表填 `redness` / `level`：

```ts
// web/heroes.ts:128 —— 携带兵力
troopCapacity(level, redness) = level × 100 + 5000 + redness × 200
//   40 级 0 红 = 9000 ｜ 50 级满红 = 11000（差 +2000）

// web/heroes.ts:96 —— 自由属性点总额
freePointBudget(heroId, redness, level)
  = floor(level / 10) × (女 15 / 男 10) + redness × 10
//   40 级 0 红（男）= 40 点 ｜ 50 级满红（男）= 100 点（差 +60）
```

**"每升一红获得 10 点属性点"与你的口径完全一致**，无需改引擎。

> 实现要点：`buildGeneral(heroId, skills, freePoints, position, redness, level, ...)` 是现成入口，但注意它**把 level 夹在 40~50**（`web/heroes.ts:313`）。红度阶梯正好落在 40 与 50 两端，不冲突。

### 5.3 卡池的展示要求

- 每个武将卡显示：**红度（红/金星）**、等级、兵力上限、已装配战法、**还差几次满红**
- 重复获得时给**明确的即时反馈**（"张辽 2 红 → 4 红：属性点 +20"）——这是抽卡的正反馈来源，不能静默处理

## 六、胜负判定（斩首制 + 兵力比兜底）

引擎本身就是**斩首制**：一侧**大营**阵亡即分胜负并**提前结束战斗**，不是三将全灭——`tests/victory.test.ts:39` 显式断言"大营阵亡、前锋中军仍存活 → 判 win 且战斗提前结束"。打满 8 回合双方大营都活时，引擎返回 `draw`，由 App 层 `judgeOutcome()` 按**剩余兵力比例**判高者胜（`web/battleSim.ts:159`，用户 2026-09-27 口径）。

| 结果 | 判据 | run 内后果 |
|---|---|---|
| **胜** | 敌方大营阵亡；或 `draw` 且我方兵力比更高 | 玉符 + 随机 S/A 战法或宝物 → 进下一关 |
| **败** | 我方大营阵亡；或 `draw` 且我方兵力比更低 | 扣 1 条命，**可换阵容重打本关**，无奖励 |
| **真平** | `draw` 且双方兵力比完全相同（**实测 0 / 1200 场**） | 不扣命、无奖励、可重打 |

**命数 = 3**：扣光则 run 结束。

> **设计后果**：斩首制让"**谁能打到敌方大营**"成为配将的核心轴（站位距离：前锋↔敌大营 = 3，大营↔敌大营 = 5），攻击距离与站位因此不是数值堆叠能替代的战术维度。叠上"兵力跨关累计"，就得到一个漂亮的压力点：**大营的残兵就是下一关的致命弱点**。

## 七、越界机制（v1 预留，不实现）

用户口径：特殊关卡给予"突破传统机制的奖励"，**v1 暂且不定**。因此本节只保留**接口与研究工作**，实现方 v1 **不要做**：

**原设计主张**（保留为 v2 的方向）：把率土的规则本身当卡池——越界卡 = 把原本只属于某个战法的特权变成玩家手里的一张牌。三层递进：L1 改**装配**（跨武将战法 / 槽位 +1）→ L2 改**卡面**（战法/武将专属强化）→ L3 改**规则**（全队主战法必发 / 全队再发动）。

**已完成的可行性核查（零引擎改动，逐条有代码证据）**：

| 候选卡 | 实现路径 | 证据 |
|---|---|---|
| 跨武将战法 | 绕过 `hero-utils.mainSkillSlot()` 的归属假设，把来源武将的主战法塞进槽位数组 | 引擎只按 `general.<slot>` 数组取战法，不校验来源（`action.ts:2977/3020/8711`） |
| 战法槽 +1 | 同上，槽位数组无长度校验 | 13 处 `for (const id of unit.general.xxxSkillIds)` 全是无界遍历 |
| 全队主战法必发 | 合成一类指挥：`{ phase:'prep', targetSide:'ally', targetMode:'all', output:[trigger_boost{rate:1, mainSkillOnly:true}] }` | `action.ts:917` 明写 `targetSide==='ally'` → 我军全体（先例：金匮要略 / 大赏三军） |
| **全队再发动**（最强候选） | 合成指挥战法 `{ allyRecast: { rate:100, factor:1, everyCast:true } }` | `allyRecast` 是引擎正式特性（`types.ts:1398`，`action.ts:8699` 读取） |

**若将来要做**：命名空间用 `rogue:<cardId>:<baseSkillId>`，战报可读名照 `src/engine/treasure-source.ts` 的 `treasure:` 前缀模式写；越界贡献在战报页按前缀聚合置顶（"爽感证据链"）。

**v2 的卡池生成思路**（已识别可借用的引擎高级钩子）：`allyRecast` / `extraByTroopRatio` / `allyActEvery` / `oncePerRoundPerTarget` / `allyActiveCastStack` / `onPrepareStart` / `mainSkillOnly` 等过滤位 → **卡池 = "钩子 × 参数"的组合空间**，不是手写若干张。

| 伤兵经济 | `WoundedMortalityConfig`（每 100 伤害死 5 伤 95；伤兵池每回合 -14%） |
| 地形与攻守 | `BattleConfig.fieldBattle`、`defenderSide`（野地/城池、攻守方） |

### 8.2 硬约束：v1 不修改 `src/engine/**`

引擎有 `tests/__snapshots__/golden.json` 逐字节快照 + 238 个测试文件，是本方案唯一的正确性资产。任何需要改引擎才能实现的效果一律**推迟或改用现有钩子**。

**验收判据（注意工作区本就不干净）**：工作区存在用户**在飞的 48 项未提交改动**，其中含 `src/engine/action.ts`、`src/engine/types.ts`、`src/data/skills.ts`。所以判据不是"相对 HEAD 无 diff"，而是：

1. 用户先提交/暂存自己的改动（推荐），或开工前存档 `git diff --stat src/engine` 作为基线；
2. 此后 **相对该基线无新增 `src/engine` 改动**；
3. 且 `npx vitest run tests/golden.test.ts` 全绿。

> **测试基线（实测）**：`npm test` = **2685 passed / 2 failed / 244 files**。两个失败**改动前就存在**、与本方案无关：`tests/battle_sim.test.ts:217`（对手池导入期望"1 队"实得"2 队"）、`tests/sim_expectation.test.ts:556`（组合榜单长度期望 >1 实得 1）。**验收不要写"npm test 全绿"**——那会逼实现者去修别人的 bug。

### 8.3 玩法层与表现层的纪律

`src/rogue/`（纯逻辑）**零 DOM、零 `localStorage` 直连**：

- 存档走注入的 `StorageLike` 接口
- 队伍构建走注入的 `buildGeneral` 依赖（**不 import `web/heroes.ts`**）

理由：这两条让玩法层将来能整体搬进 Unity（§9.3）而不用改写。

### 10.1 实测基线（已实测，非估算）

探针 `scripts/_rogue_probe.mts`：4 支**真实阵容**、全部有序对 × 100 场 = **1200 场**，数据源 `web/data/opponent_benchmark.json`，口径全走生产代码（`generalsOf` + `runBattle` + `judgeOutcome`）。

| 指标 | 实测值 | 含义 |
|---|---|---|
| 斩首结束（大营阵亡，提前结束） | **47.6%** | 斩首制确实生效 |
| 打满 8 回合 → 兵力比判定 | **52.4%** | `judgeOutcome` 兜底承担一半场次 |
| **真平（兵力比完全相同）** | **0.0%（0 / 1200）** | §六 的"真平"规则实践中不触发 |
| 先手方胜率 | 49.8% | 无先后手偏向，数据可信 |
| **平均实际回合数** | **7.47 / 8** | ⚠️ 见下 |
| 回合分布 | 8 回合 **73.3%** ｜ 7 回合 11.7% ｜ 6 回合 7.8% ｜ 5 回合 4.9% ｜ **≤4 回合 2.3%** | ⚠️ 见下 |

**结论**：基线互殴里**几乎没有"碾压"**（≤4 回合仅 2.3%）。这恰恰**量化了抽卡/买战法的价值**：变强的可观测形态不只是"胜率上升"，更是**"把 8 回合僵持变成 3 回合斩首"**。§十三 的验收因此包含"斩首回合分布左移"。

**待补**：本组是"同类阵容互殴"，不代表"玩家成长后的卡池 vs 程序生成的敌人"。目标胜率曲线需按"敌人生成器 + 目标胜率"单独标定后才能写死。

## 十三、验收标准（v1.0）

**功能**

1. 开局 3000 玉符 → 能做 **3 次五连抽**，每次都能走完"五连抽 → 五选一 → 爽玩"三步，卡池从 0 增至 ≈6 将
2. 初始战法背包含 **D/C/B 全部（166 个）**；商店能买 **A/S**，已拥有不再上架，玉符不足时按钮禁用
3. 同一武将第 2/3/4 次获得时，红度按 **2 / 4 / 5** 递进，第 4 次等级升到 **50**，卡面即时反映；兵力与属性点符合 §5.2 两条既有公式
4. 通关给玉符 + 随机 S/A 战法或宝物；被斩首扣 1 条命；命数归零结束
5. 能连打 **3 关**不崩；中途刷新不丢任何状态（卡池/红度/战法/玉符/命数/进度）

**成长可量化（不靠主观感受）**

6. 用蒙特卡洛（`web/winRate.ts`，≥100 场）证明：**同一关同一阵容，卡池成长后胜率上移**
7. 且**斩首回合分布左移**：基线是"73.3% 打满 8 回合、≤4 回合仅 2.3%"（§10.1 实测）。成长后斩首回合**中位数应从 8 回合降到 ≤5 回合**——"赢"和"碾压"是两种不同的爽感，后者才是抽卡复利的证明
8. 失败时战报页能指出具体败因（不是"打不过"）

**工程**

9. `src/rogue/` 零 DOM、零 `localStorage` 直连（用 grep 可验证）
10. 引擎零改动：相对 §8.2 冻结的基线，`src/engine` 无新增 diff；`tests/golden.test.ts` 全绿；全套失败集不超过既有 2 项
11. 单场结算 < 100ms
12. 抽卡定价、品级、红度阶梯、关卡曲线**全部是参数表**（`economy.ts` 等），改数值不需要改逻辑
