## 1. 第一性原理：这个系统到底在算什么

剥到不能再剥，全仓只有 **7 个概念**：

| # | 概念 | 形态 |
|---|------|------|
| 1 | **数据**（武将 / 战法 / 宝物 / 兵种 / 称号） | 只读事实，唯一真源 |
| 2 | **配置**（3 槽 × {将, 等级, 加点, 兵种, 特性, 宝物, 战法[]} + 环境{士气, 回合, 靶子}） | 唯一输入类型 |
| 3 | **战斗** | `配置 → 事件流`（纯函数、确定性、无全局态） |
| 4 | **读数** | `事件流 → 指标`（一次遍历产出全部口径） |
| 5 | **胜负** | `事件流 → 结果`（斩首 / 兵力） |
| 6 | **搜索** | `配置 × 维度 × 目标 × 预算 → 榜单` |
| 7 | **渲染** | `指标 / 事件流 → DOM`（无聚合、无文本反解析） |

由这 7 个概念直接推出 **5 条硬规则**（违反任意一条就是冗余或兜底）：

- **R1 一个概念一个类型**：队伍只有一个类型；"顾问方案 / 预设 / 对手条目 / 布局"都是它的**视图**或**存档**，不是平行类型。
- **R2 每个派生量只有一个计算处**：伤害、胜负、统计、贡献占比各只有一份实现；第二份 = 口径漂移。
- **R3 依赖单向**：`数据 → 引擎 → 读数 → 搜索 → 视图 → 装配`；任何人不得反向 import。
- **R4 文本只出不进**：事件里带的字段是**结构化**的；中文 `detail` 只许渲染，不许被解析回来。
- **R5 不确定就报错，不给默认值兜**：静默默认值 = 把"数据缺失"变成"另一个版本的行为"。

现状与这 5 条的差距，就是下面第 3~5 节的清单。

## 3. 冗余清单（一个功能，N 套实现）

### R1 伤害期望：两套引擎并行维护（最贵的一处）

| 维度 | 解析栈 | 真引擎栈 |
|------|--------|---------|
| 入口 | `web/roundModel.ts:342 simulateRounds`（经 `teamConfig.ts:342 computeResult`） | `web/simExpectation.ts runSimExpectationAsync` |
| 伤害来源 | 解析式重写（`roundModel.ts:1-26` 自述口径与近似） | `runBattle` 真跑 |
| 搜索 | `web/optimizer.ts:459` | `web/simExpectation.ts:1230` + `web/simMate.ts:1089` |
| 测试 | `tests/damage_model.test.ts`、`round_model.test.ts`、`optimizer.test.ts` | `tests/sim_expectation.test.ts`、`sim_mate.test.ts` |
| 页面 | `damage-model.html` / `round-model.html` / `optimizer.html` | `optimize.html` / `advisor.html` |
| 规模 | **2,939 行**（不含 `damageModel` 报表 1,065 行） | **2,884 行**（不含视图） |

两者回答的是**同一个问题**（"哪套配置伤害期望更高"）。解析式的唯一优势是秒级返回；它同时是**近似的**（`roundModel.ts:23-24` 自列 4 条近似），并且引擎公式一改就得跟着改——这就是双份真源的成本。

### R2 胜负口径 4 套（同上表 #3）

`winRate.ts:4-8` 的注释自己写明了："兵力比较仍复用 L4 `judgeOutcome`，胜/平/负归并按本模块口径"——**同一场战斗的结果，取决于你在哪个模块里问**。

### R3 跑批循环 6 处

每个循环都要自己处理：种子推进（`baseSeed + i`）、奇偶场交换红蓝（`swapSides`）、进度上报、场次统计。`web/winRate.ts:9-12` 甚至把"每颗种子跑正反两场"这条口径**又抄了一遍**（`DEFAULT_ENV` 里已有 `swapSides`）。

### R4 事件汇总 4 份 + 渲染 4 份

同一个 `BattleEvent[]`，汇总实现散在：`src/engine/stats.ts`（3 个函数各遍历一遍）、`src/engine/diagnosis.ts`（自有账本）、`web/battleSim.ts:175`、`web/damageLab.ts:373`；渲染实现散在：`src/engine/report.ts`、`web/battleView.ts`、`web/battleSummary.ts`、`web/rogue/report.ts`。

**接口形状的硬伤**：`computeDetailedStats(events, units: UnitState[])` 实际只用 `id / name / side` 三个字段，却要求调用方构造**完整** `UnitState`。于是每个调用方都得造壳：

| 造壳处 | 代码 |
|--------|------|
| `src/engine/report.ts:74-75` | `{ general: g, side, troops: 0, ..., statuses: [], preparations: [] }` |
| `web/battleSummary.ts:21-30 unitsFromReport` | 同上 |
| `web/rogue/report.ts:71 unitStub` | 同上 |
| `tests/stats.test.ts` / `split_stats.test.ts:66` / `stats_credit.test.ts:51` / `prepared_stats.test.ts` / `stats_detail.test.ts:49` | 同上（测试里再抄 5 遍） |

全仓 `statuses: [],` 出现 **171 次** —— 其中绝大多数是各测试文件自建的 `dummy()` 工厂。**没有共享的 fixture 工厂**，是"接口要求过多"的直接代价。

### R5 队伍表示 7 种

## 6. 目标架构（第一性原理）

### 6.1 最小模块集（7 个）

| 层 | 模块 | 独占职责 | 从现状吸收 |
|----|------|---------|-----------|
| 数据 | `src/data/*` | 只读事实；**唯一真源**（JSON 为生成物、DB 退为生成器） | `skills/heroes/listing/treasures/titles/secondaryTroops`（下架改成 `offlineReason` 字段） |
| 引擎 | `src/engine/battle.ts` | `battle(cfg) → events`；纯函数、无全局态、不 import 本层之外 | `combat.ts` + `action.ts`（内部私有，不再导出 60 个时机钩子） |

### 6.2 依赖规则（单向，可 lint 强制）

```
src/data  →  src/engine  →  src/search  →  web/view  →  web/app
                                    ↑
                          scripts/*、src/rogue 与 web/app 同级（消费者）
```

- `src/rogue`、`scripts/*` 与浏览器共用同一个公开 API（不是 import `web/` 内部文件）。
- 渲染层不许出现 `computeXxx`（聚合）、`parseXxx(detail)`（文本反解析）、`judgeXxx`（口径判断）。
